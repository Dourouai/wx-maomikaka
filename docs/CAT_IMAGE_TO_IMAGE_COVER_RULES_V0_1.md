# 猫咪咔咔｜猫咪图生图封面规则 v0.1

> 状态：规则、首版代码和线上验收均已落地；`poster-cover` 已接入海报加载链路并在 `yangxi-studio` 完成部署，`cat-transform` 仍保持主体抠图职责。
>
> 用户提供的海报截图只作为视觉参考，不是可执行提示词，也不是猫咪数据来源。

## 1. 一句话定义

输入一张已经通过安全检查的猫咪照片，尽可能保留同一只猫的真实身份和主体细节，只为它生成一个适合放进猫档案海报主图区域的真实照片场景；文字、等级、编号、边框和图标全部由 Canvas 负责。

这里的“封面图”不是完整海报，也不是重新画一只更好看的猫。

## 2. 必须区分的两个图像产物

| 产物 | 作用 | 是否允许生成背景 | 是否允许改变猫 | 当前状态 |
| --- | --- | --- | --- | --- |
| `subject` 主体图 | 保留猫咪，移除原始背景，输出透明 PNG | 否 | 否 | 已有 `cat-transform` 的 `matting` 链路 |
| `poster-cover` 封面图 | 给猫咪配一个新的场景，用于海报主图区域 | 是 | 否 | 新增独立业务链路，复用 `cat-transform` 当前使用的模型 |

“封面图”是新增的一条链路，不是把现有 `cat-transform` 的 `matting` 改成另一种模式。原有主体图接口和提示词保持不变；新链路可以复用同一个模型、服务地址和鉴权配置，但必须使用独立的函数入口、提示词、操作名、版本和结果字段。原图、主体图和封面图必须分别保存，失败时可以互相回退，但不能用一张失败的 AI 图片覆盖事实原图。

## 3. 不可违反的身份保真规则

### 3.1 猫咪必须保持不变

图生图可以生成或修改背景、光线和空间氛围，但不能重新设计猫咪。必须尽量保持：

- 脸部轮廓、眼睛颜色和形状、鼻子、嘴巴、胡须；
- 耳朵数量、耳形、耳缘绒毛和缺口；
- 毛色、花纹、斑块、胸口颜色、爪子颜色和尾巴特征；
- 身体比例、头身关系、姿态、动作、朝向和可见四肢；
- 项圈、铃铛或其他原图中确实存在的可见物件；
- 毛发边缘、飞毛、绒毛和真实照片质感。

禁止把“保留猫咪”理解成只保留一个相似轮廓。只要脸、花纹、眼睛、肢体或尾巴明显被重绘，就视为封面图失败。

### 3.2 不允许补造不确定的猫咪细节

- 原图已经存在的部分不能重绘；
- 原图被边缘裁掉的部分不强行臆测补全；
- 不增加眼睛、耳朵、腿、爪子、尾巴或第二只猫；
- 不把背景中的植物、家具、影子或布料粘到猫身上；
- 不用“美化”“换品种”“变年轻”“更可爱”等词引导模型修改猫。

如果原图主体本身不完整，优先使用现有主体处理链路获得可用的透明主体；无法可靠补齐时使用原图裁切，不把不确定的补全结果当成正式封面。

## 4. 封面图的尺寸与构图

### 4.1 目标比例

封面图要放进当前 `9:16` 海报的主图区域，所以目标不是整张海报的 `9:16`，而是：

- 海报 Canvas：`750 × 1334`；
- 主图区域：`718 × 1074`；
- 主图目标比例：`359:537`，约 `0.67:1`；
- 信息区从 `y=1090` 开始，封面图不能侵入信息区；
- 服务返回的尺寸可以不同，但进入 Canvas 前必须按 `359:537` 做不拉伸的裁切或留边。

整张海报的 `9:16` 只传给海报 Canvas，不直接作为封面图服务的目标尺寸。

### 4.2 构图安全区

- 猫咪优先位于画面中心或略偏下，保证脸部、耳朵、四肢和尾巴可见；
- 猫咪主体整体外接矩形控制在画面面积约 `8%–15%`，主体高度约为画面高度的 `22%–30%`，宽度不超过画面宽度 `45%`；至少保留约 `70%` 的可见环境空间；
- 头顶、耳朵和尾巴边缘保留安全留白，不贴边裁切；
- 背景可以有景深和光线，但不能比猫咪更抢眼；
- 封面图必须能直接被 Canvas `cover` 放入主图区域，不依赖用户手动拖动或再次裁切；
- 不能把海报标题区、评分区或底部指标区画进封面图。

## 5. 输入规则

### 5.1 输入优先级

```text
通过安全检查的原始照片
  → 已通过检查的透明猫咪主体图
  → 没有可用输入：不生成封面图
```

首版实际只把通过安全检查的原始照片作为模型垫图传入，并把 `targetRatio = 359:537` 和服务端通用提示词交给云函数。当前模型的 `images` 垫图参数按接口只接收一张图，因此主体 PNG 不与原图同时传给模型；已有主体 PNG 只作为没有原图 fileID 时的旧记录兜底。客户端传入的 `sceneSeed` 只用于服务端从场景族中稳定选择本张图的背景方向，不把内部编号或原始值拼进模型可见文案。

### 5.2 不作为输入的内容

- `openid`、用户昵称、精确位置、设备编号；
- `archiveCode`、`recordId`、分享链接和内部文件路径；
- MIKA 分数、三项评分、等级名称和奖励数据；
- Canvas 上的标题、标签、边框、图标和 UI 截图；
- 另一张已经生成的封面图作为下一次生成的唯一事实来源。

## 6. 生成策略

### 6.1 生产优先级

严格保真时，优先采用“猫咪前景 + AI 背景”的合成思路：

```text
原图安全检查
  → 得到可靠主体 PNG
  → 生成无文字、无猫或只包含环境的背景候选
  → 保持主体 PNG 不变地合成到背景
  → 按 359:537 裁切
  → 质量检查
```

当前首版使用整图图生图：由新增的 `poster-cover` 链路调用 `cat-transform` 当前使用的同一个模型，输入原图，输出猫咪与手绘背景的完整合成图。客户端在进入 Canvas 前按 `718×1074` 主图框裁切；整图图生图结果必须经过更严格的猫咪保真检查，不能因为背景好看就直接通过。后续如果模型支持稳定的蒙版或独立背景生成，再升级为前景不重绘的硬合成方案。

### 6.2 正向提示词的层级

每次请求的服务端提示词按以下顺序组织，用户输入只能影响场景主题，不能覆盖身份规则：

1. **任务类型**：真实照片封面场景生成，不是完整海报，不是插画，不是换猫；
2. **主体锁定**：输入图片中的唯一猫咪是唯一主角，保持脸、花纹、眼睛、体型、姿态和毛发；
3. **场景生成**：从服务端场景族中选择一个明确且与其他猫卡不同的主题，生成自然、克制、能衬托猫咪的背景和光线；
4. **构图**：适配 `359:537` 竖版主图，猫咪保持小比例环境主体，脸和四肢不被裁掉；
5. **输出限制**：真实照片质感、无文字、无 Logo、无水印、无相框、无卡片版式。

### 6.3 反向约束

每次请求都必须禁止：

```text
第二只猫、重复猫、猫脸变化、花纹变化、换品种、额外眼睛、额外耳朵、
多余四肢、断尾、残肢、融化、塑料毛发、动漫、插画、3D、玩偶、油画、
海报、卡片、边框、标签、编号、中文、英文、乱码、Logo、水印、品牌字样、
相机界面、截图、地面大面积遮挡、背景残留粘连、棋盘格、白色抠图底。
```

提示词不能要求模型在图片里写任何海报信息。所有文字由 Canvas 在后续绘制。

## 7. 生成参数和版本规则

当前项目的图片服务使用 CloudBase `hunyuan-image` 图生图链路。封面图新增独立的 `poster-cover` 业务链路，但复用 `cat-transform` 当前的模型配置：

```text
existing function: cat-transform
existing operation: image-to-image-subject-only
existing model: HY-Image-v3.0-I2I-ToB-v1.0.1

new function: poster-cover
operation: image-to-image-poster-cover
coverVersion: cat-cover.v0.3
promptVersion: cat-cover-prompt.v0.3
targetRatio: 359:537
```

参数规则：

- `poster-cover` 与 `cat-transform` 使用同一供应商、同一模型和同一图片服务路线；这表示复用模型能力，不表示复用主体抠图接口；
- 首版请求尺寸固定为 `718x1074`；CloudBase 返回尺寸若有差异，Canvas 仍按 `359:537` 进行不拉伸裁切；
- `cat-transform` 的 `matting` 仍只输出透明主体 PNG，不负责生成场景封面；
- `poster-cover` 输出完整、不透明的猫咪与手绘背景合成图，目标比例为 `359:537`；
- 优先使用低到中等的重绘强度，确保猫咪不被重新设计；具体参数以服务实际支持能力为准；
- 关闭提示词改写或等效能力，避免服务端把任务扩写成海报创作；
- `poster-cover` 请求按产品要求传 `footnote: '·'` 作为轻量自定义标识；它不是海报档案文字，Canvas 仍负责姓名、编号、等级、分数和文案；
- 不把 `footnote` 或 `LogoAdd` 当成关闭平台强制标识的可靠方案；除约定的轻量标识外，如果服务返回明显 AI 标识、额外文字或水印，结果标记为失败，不用后处理覆盖或擦除；
- 所有服务端密钥只存在云函数环境变量中，小程序端只拿临时图片地址或结果状态。

## 8. 输出数据契约

每条记录分别保存原图、主体图和封面图。推荐新增字段：

```json
{
  "coverFileID": "cloud fileID",
  "coverPhotoPath": "temporary local URL",
  "coverContentType": "image/jpeg",
  "coverProvider": "hunyuan-image",
  "coverModel": "HY-Image-v3.0-I2I-ToB-v1.0.1",
  "coverOperation": "image-to-image-poster-cover",
  "coverPromptVersion": "cat-cover-prompt.v0.3",
  "coverTargetRatio": "359:537",
  "coverStatus": "ready",
  "coverRequestId": "provider request id",
  "coverCreatedAt": "ISO date",
  "coverRejectReason": ""
}
```

字段规则：

- `originalFileID` 永远保留，代表用户真实输入；
- `cutoutFileID` 只代表透明主体处理结果；
- `coverFileID` 只代表通过验收的封面候选；
- 生成失败或验收失败时，保留失败原因，但不能写入 `coverFileID` 作为可用图；
- 首次通过验收的封面写入对应 `sourceRecordId` 的 `cover*` 字段并固定复用；同一条记录再次生成海报时不得重复调用 AI；
- 只有用户明确触发“重新生成”时才创建新的请求 ID 和版本记录，不覆盖原图，也不改变 `archiveCode`；
- 分享海报只使用通过验收的封面图或回退图，不把模型提示词、原始位置和内部 ID 放入公开快照。

## 9. 状态机和回退规则

```text
idle
  → checking-source
  → generating-cover
  → downloading-result
  → validating-cover
  → ready
```

失败状态包括：

- `SOURCE_IMAGE_UNAVAILABLE`：没有可靠原图或主体图；
- `COVER_PROVIDER_UNAVAILABLE`：服务未配置、超时或调用失败；
- `COVER_RATIO_INVALID`：结果无法适配 `359:537`；
- `COVER_IDENTITY_CHANGED`：猫咪身份或结构发生明显变化；
- `COVER_CONTENT_INVALID`：出现文字、Logo、水印、第二只猫或不合规内容；
- `COVER_QUALITY_LOW`：主体过小、模糊、严重遮挡或边缘异常。

回退顺序固定为：

```text
通过验收的 coverFileID
  → 通过安全检查的原图按 359:537 cover 裁切
  → 可靠主体 PNG 放到模板背景中
  → 明确失败，不展示一张看似成功的 AI 图片
```

回退不能悄悄把失败结果当成成功，也不能为了“看起来有图”降低身份保真标准。

## 10. 封面图验收规则

### 10.1 机器检查

- 文件可读取，格式为 JPEG 或 PNG；
- 宽高比例可以无变形适配 `359:537`；
- 图片不是空文件、棋盘格、纯色底或透明假背景；
- 检测到的猫数量为 1；
- 没有 OCR 文本、Logo、边框、水印和 UI 截图；
- 猫咪主体高度约为画面高度的 `22%–30%`，整体外接矩形占画面面积约 `8%–15%`，宽度不超过画面宽度 `45%`；
- 没有明显重复的眼睛、耳朵、腿、爪子或尾巴。

### 10.2 身份检查

至少检查以下关键点：

- 眼睛、鼻子、嘴巴和耳朵的数量与原图一致；
- 花纹和主要颜色分布没有明显改变；
- 头身比例、身体朝向和动作没有明显改变；
- 尾巴、四肢和爪子没有新增、缺失或融入背景；
- 猫咪毛发边缘没有大面积树枝、地面、家具或背景污染。

现有 `glm-cat-feature` 结构化特征只能作为辅助证据，不能单独证明是同一只猫；如果关键点检查不通过，直接回退原图。

### 10.3 人工抽检

上线前至少用以下样本抽检：

- 正面、侧面、趴卧、站立和远距离猫；
- 黑猫、白猫、虎斑、三花和高反差花色；
- 尾巴细长、耳朵贴边、身体被遮挡和原图主体较小的样本；
- 室内、街道、夜间和复杂背景样本。

重点不是“背景是否漂亮”，而是“用户一眼能否认出仍然是原来那只猫”。

## 11. 海报接入规则

`posterData` 只读取已经完成验收的封面图，不在 Canvas 中调用模型：

```text
validated cover
  → posterCanvas 以 cover 模式绘制主图
  → Canvas 绘制 C / U / R / SR / UR 等级色边框
  → Canvas 绘制档案编号、姓名、文案、MIKA 和三项分数
  → 导出同一张 PNG 用于预览、保存和分享
```

封面图本身不得包含：

- 猫咪档案编号；
- 等级字母或中文等级名；
- MIKA、魅力、机灵、灵气和任何分数；
- 猫咪名字、品种、描述和海报文案；
- 外边框、标签、评分区、Logo 和分享二维码。

这样可以保证以后调整文字、编号或等级颜色时，不需要重新调用图生图，也不会把旧文字烘焙进照片。

## 12. 当前冻结结论与下一步

本轮先冻结：

1. “主体图”和“封面图”是两个独立产物，不能混用字段和版本；
2. 封面图只生成场景和氛围，猫咪身份必须保留；
3. 封面图目标比例为主图区域 `359:537`，整张海报仍为 `9:16`；
4. 优先采用可靠主体前景与 AI 背景合成，整图图生图只作为严格验收的候选方案；
5. 封面图不写任何文字、编号、等级、Logo 或水印；
6. 失败时回退到原图，不展示未经验收的 AI 结果；
7. 原图、主体图、封面图和 `archiveCode` 均独立保存、独立追溯。

首版实现已落地，代码对应关系如下：

1. `miniprogram/cloudfunctions/poster-cover/`：独立云函数，复用 `hunyuan-image`、`HY-Image-v3.0-I2I-ToB-v1.0.1` 和 `images/ar/generations`，请求尺寸为 `718x1074`；
2. `miniprogram/utils/posterCover.js`：小程序端只负责传入已通过安全检查的原图 `fileID`、接收结果和换取临时地址；
3. `miniprogram/pages/poster-loading/poster-loading.js`：本地海报首次生成时调用封面链路，失败回退原图/主体图，不阻断海报；分享档案只复用已存在的封面；
4. `miniprogram/utils/posterData.js`：只把 `coverStatus=ready` 的封面作为海报主图，并保留原图、主体图和封面图的独立字段；
5. `miniprogram/utils/storage.js`、`userData.js`、同步与分享云函数：保存和传递封面元数据，不覆盖 `originalFileID` 或 `cutoutFileID`。

2026-09-06 已在 CloudBase `yangxi-studio` 完成部署，将函数执行超时配置为 900 秒，并用 `小黑炭` C 档案完成真实样本验收：海报预览出现新的手绘动漫场景，猫咪保留为原始照片主体，未出现 `COVER_PROVIDER_UNAVAILABLE` 回退日志。后续仍需按正式发布清单补做多种姿态、毛色和边缘完整性的批量视觉验收；当前模型返回结果的视觉验收不能仅由提示词代替。
