# 猫咪咔咔 — 图片与相遇卡编号规则 v0.1

> 当前阶段：数据与卡面编号设计稿
>
> 本文只定义编号的组成、展示方式和唯一性规则，不涉及代码实现。

## 1. 编号分三层

一张用户看到的卡，需要同时解决三个问题：这次相遇是哪一次、原始图片是哪一张、猫咪档案是哪一只。

| 编号 | 面向对象 | 是否对用户展示 | 是否稳定 |
|---|---|---|---|
| **相遇卡编号** `cardNo` | 一次有效拍摄生成的相遇卡 | 是，印在卡面上 | 永不改变 |
| **图片编号** `imageId` | 原始照片和每个衍生图片文件 | 详情页可展示 | 文件级稳定 |
| **猫咪档案编号** `catId` | 被识别并建立的同一只猫 | 图鉴详情可展示 | 同一只猫保持不变 |

核心关系：

```text
1 个罐罐
  ↓
1 张有效原始图片 imageId
  ↓
1 张相遇卡 cardNo
  ↓
1 个目标猫咪 catId
```

同一只猫再次被拍到时，`catId` 不变，但会产生新的 `imageId` 和新的 `cardNo`。

## 2. 用户可见的相遇卡编号

推荐格式：

```text
MK-YYMMDD-NNNNNN
```

示例：

```text
MK-260902-000014
```

字段含义：

| 部分 | 含义 |
|---|---|
| `MK` | Maomi Kaka / 猫咪咔咔品牌前缀 |
| `260902` | 生成日期，按 Asia/Shanghai 自然日 |
| `000014` | 当天全平台递增序号，固定 6 位 |

卡面建议展示：

```text
No. MK-260902-000014
```

如果卡面空间很小，可以大字展示 `#000014`，但详情页和分享图必须保留完整的 `MK-260902-000014`。短号只能作为视觉缩写，不能单独作为唯一编号。

## 3. 图片编号

每个图片文件都要有自己的 `imageId`，包括：

- 用户上传的原始照片；
- 裁剪或压缩后的服务端版本；
- 可选的风格化卡面图；
- 后续生成的缩略图。

推荐内部格式：

```text
IMG-{ULID}
```

示例：

```text
IMG-01K6Q3JY8KQ9P2W7A4D6N1M8TZ
```

`ULID` 用于保证多用户并发上传时仍然唯一，并且大致按创建时间排序。图片编号不编码等级、分数、地点或用户身份，避免信息变化后编号失效或泄露隐私。

## 4. 猫咪档案编号

猫咪档案编号用于关联同一只猫的多次相遇：

```text
CAT-000378
```

规则：

- 只有识别结果通过质量门槛并建立档案后，才创建 `catId`；
- 同一只猫重复出现，继续使用原来的 `catId`；
- 暂时无法确认是否为同一只猫时，先保留新的临时档案，不强行合并；
- `catId` 不包含品种、稀有等级或猫咪名称，因为这些字段未来可能修正。

## 5. 唯一性与生成时机

### 相遇卡编号

- 由服务端生成，不由小程序本地生成；
- 当图片通过质量门槛、服务端接受本次拍摄时生成；
- 当天序号使用原子递增，不能依赖“当前已有数量 + 1”；
- 多个用户同时拍摄时也不能重复；
- 失败、取消或重复请求可能产生跳号，允许跳号，但编号永不复用；
- 卡片删除后只做隐藏或软删除，原编号永久保留。

### 图片编号

- 图片一上传就分配 `imageId`；
- 网络重试使用同一个上传任务 ID，不能为同一张重试图片生成多个原始图片编号；
- 对完全相同的文件计算内容哈希，避免重复上传重复发卡；
- 同一张原图生成不同尺寸或风格时，衍生文件使用新的 `imageId`，并保存 `parentImageId`。

## 6. 重复、失败和编辑规则

| 情况 | 编号处理 | 奖励处理 |
|---|---|---|
| 图片模糊 / 不是猫 / 不符合收录条件 | 可有内部 `imageId`，不生成 `cardNo` | 已提交任务的 1 个罐罐不返还；不发猫爪和咔咔分 |
| 快门前取消 / 相机权限失败 | 不创建拍摄任务，不生成 `cardNo` | 没有提交任务，不扣罐罐 |
| 上传重试 | 沿用原上传任务和 `imageId` | 只结算一次 |
| 服务端或系统异常 | 可有内部 `imageId`，不生成 `cardNo` | 返还已扣除的罐罐，不发奖励，允许重试 |
| 服务端超时但结果未知 | 通过幂等键查询原结果 | 不重复发卡、不重复发奖 |
| 快门后退出页面 | 继续使用原拍摄任务的编号关联 | 按任务最终状态结算，不能因未打开结果页自动返还 |
| 同一只猫再次拍摄 | 新 `imageId` + 新 `cardNo`，复用 `catId` | 按本次咪咔重新结算 |
| 重新生成卡面风格 | 新衍生 `imageId`，保留原 `cardNo` | 不重复发奖励 |
| 用户删除卡片 | `cardNo` 保留，记录置为隐藏 | 不返还历史奖励 |

## 7. 结果卡展示示例

```text
✦ CAT FOUND ✦

橘色小家伙
R · [中文标签待定]
咪咔 75

猫爪 +115       咔咔分 +8

No. MK-260902-000014
猫咪档案 CAT-000378
```

原始图片和卡面图的 `imageId` 不需要占据结果卡主视觉，可放在卡片详情的“图片信息”中。

## 8. 编号不承载业务属性

编号里不放以下信息：

- 咪咔分数；
- N / C、U、R、SR、UR 等等级；
- 猫咪名称或品种；
- 用户 ID；
- GPS 位置；
- 模型版本。

这些字段都可能被修正或重新识别，而编号应该始终保持稳定。

## 9. 当前建议

首版对外只突出一个编号：`cardNo`。图片编号和猫咪档案编号作为详情和数据库关联字段保存，避免用户一次看到太多技术编号。
