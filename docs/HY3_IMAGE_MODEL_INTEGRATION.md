> 状态：当前版本接入 TokenHub GLM-5.3-Flash 图片理解 → CloudBase 混元图生图主体处理 → 入图鉴链路
>
> 更新时间：2026-09-02
>
> 业务侧简称：HY3

## 1. 文档目的

记录 HY3 相关模型的服务端接入方案，作为服务端接口、微信小程序调用和猫咪主体卡片流程的实施依据。

当前按 CloudBase 官方 `wx-server-sdk` 方案拆分为视觉理解和主体图处理两层；本版本不调用 Hy3 文本模型，先由 GLM 视觉模型在严格长度和事实边界内返回品种、猫咪昵称和简短描述。

## 3. 业务定位

### 3.1 视觉模型：GLM-5.3-Flash

视觉模型负责读取用户拍摄的照片，输出结构化识别结果和一段受约束的展示文案：

- `isCat`：是否发现猫咪；
- `catCount`：画面中的猫咪数量，第一版只收录单猫照片；
- `breed`：从图鉴支持的标签中选择最接近的品种，无法判断时返回“未知品种”；
- `confidence` 和最多 3 个外观特征；
- `name`：根据可见毛色、花纹、姿态或神态生成的有趣中文昵称，最多 5 个字符；
- `description`：基于照片可见内容生成的轻松短描述，最多 50 个字符；
- `scoreEvidence`：魅力、机灵、灵气各自的可观察子项，均为 0–100 分；服务端按 `cat-score.v0.2` 固定权重计算 `scores`，再用于计算咪咔并映射相遇等级。

当前通过 TokenHub OpenAI 兼容的 `/v1/chat/completions` 调用 `glm-5.3-flash`。图片以 Chat Completions 的 `image_url` 内容块传入 Base64 Data URI；TokenHub API Key 只保存在 `cat-vision` 云函数环境变量中，不进入小程序或代码库。TokenHub 的 GLM-5.3-Flash 多模态示例也使用该接口。

### 3.2 文本模型：Hy3（当前版本不调用）

Hy3 后续可以负责更长的卡片文案，但当前版本不调用它。猫咪昵称和 50 字以内的描述直接由 GLM 在看图后生成，并由服务端做长度清理；生成失败时回退到本地图鉴固定名称和描述，不影响原始拍摄记录。

建议用途：

- 生成猫咪卡片标题和昵称；
- 根据已确认的品种、外观特征、时间和地点生成小故事；
- 生成卡片标签、性格描述和简短介绍；
- 把结构化卡片信息转换成适合图像模型的提示词；
- 根据用户选择的主题生成不同风格的文案。

建议输入：

```json
{
  "scene": "cat_card",
  "catDetection": {
    "isCat": true,
    "breed": "短毛橘猫",
    "confidence": 0.86,
    "traits": ["橘色毛发", "短毛", "圆脸"]
  },
  "capture": {
    "capturedAt": "2026-09-01T13:00:00+08:00",
    "locationText": "上海·静安区"
  },
  "userNote": "它一直蹲在便利店门口晒太阳",
  "style": "温暖、治愈、轻松"
}
```

建议输出为严格 JSON，而不是直接返回一大段自由文本：

```json
{
  "title": "阿橘队长",
  "story": "它像是这条街的值班员，每天准时在门口迎接路过的人。",
  "traits": ["慵懒", "亲人", "有领地意识"],
  "description": "一只在午后阳光里守护便利店门口的橘猫。",
  "imagePrompt": "温暖治愈的猫咪收藏卡片插画，橘色短毛猫，午后阳光，街角便利店，干净构图",
  "negativePrompt": "多只猫、额外肢体、文字、水印、畸形眼睛、严重改变毛色"
}
```

约束原则：

- 品种、地点和拍摄时间以视觉识别结果或用户数据为准，Hy3 不应自行编造事实；
- 识别置信度不足时输出“未知品种”或中性描述；
- 用户备注作为数据输入处理，不能覆盖系统规则或注入模型配置；
- 服务端校验 JSON 字段、字数、敏感内容和提示词版本后，才交给图像模型；
- 文本生成失败时可以使用固定模板，不影响原始拍摄记录保存。

### 3.3 文生图模型

模型：`HY-Image-3.0-Plus-4090-Tob-v1.0`

建议用于不依赖用户原图的视觉内容：

- 猫咪卡片背景；
- 节日、季节和活动主题插画；
- 卡片边框、贴纸、徽章和氛围装饰；
- 空状态、加载页和分享海报的视觉素材。

文生图结果不应直接作为“用户拍到的真实猫咪照片”，而应标记为背景、插画或装饰素材。

### 3.4 图生图模型：主体处理

模型：`HY-Image-v3.0-I2I-ToB-v1.0.1`

当前仅用于尽量保留用户照片主体的图生图处理：

- 从原照片中提取同一只猫，输出适合放进图鉴容器的主体素材；
- 保留猫咪毛色、花纹、姿势、比例和完整轮廓；
- 不生成背景、贴纸、边框、标签、故事或其他装饰；
- 同时保留安全校验后的原始照片作为事实记录。

图生图结果不是严格像素级抠图，也不能替代原始照片；它是主体展示素材。当前按项目调试阶段要求，先恢复 CloudBase 的 `hunyuan-image` 图生图链路，模型为 `HY-Image-v3.0-I2I-ToB-v1.0.1`，使用 `images` base64 垫图并关闭 prompt 改写。CloudBase 服务侧可能保留平台 AI 标识，也不保证输出是真正的 alpha 透明 PNG；模型结果只用于主体展示，不作为原始事实照片。

## 4. 总体架构

```text
微信小程序
  │
  │  上传照片、提交生成请求
  ▼
业务服务端 / 云函数网关
  │  鉴权、参数校验、模型路由、任务状态
  ├──────────────► Hy3 文本模型
  │                      └── 返回卡片文案、标签和图像提示词
  ├──────────────► Hunyuan Image 模型服务
  │                      └── 返回背景图或风格化图片
  ▼
对象存储
  │  原始照片、生成图片、缩略图、元数据
  ▼
微信小程序
  └── 查询任务并展示揭示页、卡片和图鉴
```

### 4.1 必须经过服务端

- 模型 API Key、签名密钥和供应商凭证不能放在小程序代码中；
- 模型 ID、提示词模板和生成参数应由服务端控制；
- 服务端负责限制用户频率、控制成本、记录调用日志和处理失败重试；
- 小程序只接收业务侧任务 ID 和可访问的临时图片地址。

### 4.2 与现有代码的关系

当前项目的 `miniprogram/utils/identify.js` 负责猫咪识别，并使用 Mock 或占位接口返回 `catId`。图像生成是独立能力，不建议把模型生成逻辑直接塞进 `identify.js`。

后续建议拆分为：

- `cat identification`：判断是否有猫、品种或分类；
- `anti-spoofing`：照片/屏幕/视频重放检查；
- `text generation`：当前由 GLM 生成受约束的短昵称和短描述，后续再使用 Hy3 扩展卡片文案、标签和图像提示词；
- `image generation`：使用两个 Hunyuan Image 模型进行文生图和图生图；
- `card composition`：把原图、生成图、品种和故事合成为最终卡片。

### 4.3 当前实际实现

当前代码已新增以下链路：

- `miniprogram/cloudfunctions/cat-vision/`：通过 TokenHub `glm-5.3-flash` 的 `/chat/completions` 多模态接口返回 `isCat`、`catCount`、`breed`、`confidence`、`name`、`description`、`traits` 和 `scoreEvidence`，服务端规范化后返回 `scores`；
- `miniprogram/cloudfunctions/cat-transform/`：使用 `wx-server-sdk@4.0.2` 保存图片，通过 `cloud.ai().createImageModel('hunyuan-image')` 调用 `HY-Image-v3.0-I2I-ToB-v1.0.1`，以 `images: [base64]` 传入一张原图并固定使用 `images/ar/generations`；
- 小程序拍照后先调用现有 `content-security` 校验原图，再调用 `cat-vision` 判断是否为猫、映射品种并计算相遇评分，之后调用 `cat-transform` 的 `matting` 动作；任务提交后先扣除 1 个罐罐，非猫、多猫无法确认目标或图片不合格时不写入拍摄记录且不返还罐罐；识别服务不可用等产品侧异常时返还罐罐；
- 云函数使用上一版 CloudBase 链路的三句主体处理提示并关闭提示词改写，CloudBase 图生图请求只传入 `footnote: '·'`，不传 `LogoAdd`；模型结果不做二次 `security.imgSecCheck`，直接保存到 `cat-album/cutout/`；
- 本地记录同时保存安全校验后的原图 `fileID`、主体图 `fileID` 和主体处理元数据；图鉴与详情页优先展示主体图，主体处理失败时不把原图伪装成主体图；
- 主体图临时访问地址过期后，图鉴和详情页会根据持久化 `fileID` 重新换取地址；页面不展示模型提示词、生成标签或模型说明。

## 5. 推荐业务流程

### 5.1 用户拍摄流程

1. 小程序通过相机获取照片；
2. 服务端接收原图并生成 `captureId`；
3. 执行基础校验：文件类型、大小、尺寸、图片完整性；
4. 后续接入猫咪检测和防作弊检测；
5. 将视觉识别结果和用户备注提交给 Hy3，生成卡片文案与图像提示词；
6. 创建图生图任务，使用用户原图作为输入；
7. 任务完成后生成卡片视觉图；
8. 保存原图、文案、生成图和模型元数据；
9. 揭示页展示生成结果，图鉴保存本次拍摄记录。

### 5.2 文生图流程

文生图用于预生成或按需生成，不应阻塞用户“真实拍摄记录”的保存：

1. 根据卡片主题生成结构化提示词；
2. 选择 `HY-Image-3.0-Plus-4090-Tob-v1.0`；
3. 生成背景或装饰素材；
4. 通过卡片合成层与用户原图组合；
5. 缓存相同主题和版本的结果，避免重复消耗模型额度。

### 5.3 文本生成流程

1. 接收猫咪视觉识别结果、拍摄时间、可选地点和用户备注；
2. 服务端套用固定的系统提示词和输出 JSON Schema；
3. 调用 `Hy3` 生成标题、故事、标签、描述和图像提示词；
4. 服务端校验字段、字数、敏感内容和事实边界；
5. 将通过校验的 `imagePrompt` 交给图像模型；
6. 保存 `promptVersion`、结构化结果和任务关联关系。

## 7. 模型路由规则

| 业务场景 | 调用模式 | 模型 |
|---|---|---|
| 卡片标题、故事、标签和描述 | `text_generation` | `Hy3` |
| 为图像模型生成结构化提示词 | `text_generation` | `Hy3` |
| 卡片背景、节日主题、装饰素材 | `text_to_image` | `HY-Image-3.0-Plus-4090-Tob-v1.0` |
| 用户猫咪照片风格化 | `image_to_image` | `HY-Image-v3.0-I2I-ToB-v1.0.1` |
| 最终卡片排版 | 业务服务端合成 | 不直接调用模型 |
| 猫咪是否存在、是否重复、是否真实 | CV/活体检测 | 不属于图像生成模型职责 |

模型路由必须使用白名单，客户端只能提交业务场景，不能任意传入模型 ID。

## 8. 生成质量要求

### 8.1 文本模型质量要求

- 输出必须符合约定 JSON Schema，不能把模型原始长文本直接写入卡片；
- 标题、故事和标签要有长度上限，避免破坏卡片布局；
- 不得虚构品种、拍摄地点、时间或猫咪身份；
- 视觉识别置信度不足时，应使用“未知品种”等保守表达；
- `imagePrompt` 和 `negativePrompt` 使用服务端模板约束，不能完全由用户输入决定；
- 同一输入和同一 `promptVersion` 尽量保持结果风格稳定；
- 文案审核失败时，降级到固定模板文案。

### 8.2 图生图质量要求

图生图重点不是“画得好看”而是“仍然像用户拍到的那只猫”。验收时重点检查：

- 毛色、花纹、脸部特征和体型没有被大幅改变；
- 不凭空增加第二只猫、人的手、额外耳朵或肢体；
- 不生成文字、水印或品牌标识；
- 原图主体在不同角度和光线下仍可辨认；
- 失败时可以保留原图并重新生成，不丢失拍摄记录。

建议保留以下元数据：

```json
{
  "sourceAssetId": "asset_original_xxx",
  "generatedAssetId": "asset_generated_xxx",
  "model": "HY-Image-v3.0-I2I-ToB-v1.0.1",
  "promptVersion": "cat-card-v1",
  "parameters": {},
  "providerRequestId": "provider_req_xxx",
  "createdAt": "2026-09-01T00:00:00Z"
}
```

## 9. 异常、重试和降级

### 可重试错误

- 网络超时；
- 供应商 5xx；
- 限流或临时繁忙；
- 任务查询暂时失败。

建议采用指数退避，最多自动重试 2～3 次，并使用 `requestId` 或幂等键避免重复扣费。

### 不应自动重试的错误

- 图片格式或尺寸不支持；
- 内容审核不通过；
- 参数校验失败；
- 模型不存在或没有权限；
- 用户取消任务。

### 降级策略

生成失败时：

1. 保留本次原始照片和拍摄记录；
2. 展示固定卡片模板或原图卡片；
3. 给用户提供“重新生成”入口；
4. 记录失败原因和供应商请求 ID，便于排查。

不能因为图像生成失败而随机伪造一个 AI 结果，避免收藏记录与用户实际拍摄内容不一致。

## 10. 安全与隐私

- 模型密钥只保存在服务端；
- 原始照片和生成图使用对象存储，不把大图长期塞进数据库；
- 图片 URL 使用短期签名地址；
- 用户照片可能包含人脸、地理位置或其他个人信息，需要单独确认保存期限；
- 向第三方模型服务上传前，应确认数据是否用于训练、保留多久以及是否支持删除；
- 日志记录模型、任务状态、耗时、错误码和费用，不记录完整图片内容；
- 原图和生成图都应支持删除，删除卡片时同步处理关联资源。

- 输入图片支持的格式、大小和最大分辨率；
- 输出分辨率、比例和图片格式；
- 图生图的重绘强度或主体保留参数名称；
- 是否支持随机种子、负面提示词和批量生成；

- 是否提供调用量、耗时和费用查询接口。

## 12. 分阶段实施建议

### 阶段 0：接口确认

### 阶段 2：文本模型

## 13. 当前结论

当前记录三类模型职责：

- Hy3 文本模型负责卡片文案、标签、故事和图像提示词；
- 文生图模型负责通用视觉素材；
- 图生图模型负责用户猫咪照片的主体分离展示；不生成卡片文案、故事、标签或装饰。

Hy3 文本模型不替代猫咪视觉识别，也不直接证明照片中是真猫。视觉识别结果、原始照片和用户拍摄记录应作为事实层；Hy3 和图像模型负责内容表达与卡片表现层。

猫咪识别、猫咪特征向量去重和真人/照片/视频活体检测属于另外的视觉能力，不能由上述图像生成模型直接替代。后续接入时应保留原始照片，把 AI 生成图定位为卡片表现层，而不是事实证据。
